# Persistent Memory Architecture — IAM Client OS

**Status:** design approved  
**Date:** 15.04.2026  
**Author:** Ariel + Claude Opus 4.6

---

## Overview

Every IAM Client OS installation has a `memory/` directory that AI agents read at session start. This is the persistent context that survives between chat sessions. Without good memory, every new chat starts from zero.

The memory system has two goals:
1. **Make AI productive immediately** — structured context, clear instructions, project knowledge
2. **Accumulate training data** — patterns, anti-patterns, decisions → future fine-tune dataset

---

## Directory Structure

```
memory/
├── RULES.md                    ← LOCKED. Platform rules. Nobody writes, everyone reads.
├── ARCHITECTURE.md             ← WRITE-ONCE. Contains audit prompt inside. Filled on first Claude connection.
├── RECOMMENDATIONS.md          ← Improvement suggestions (created during architecture audit)
├── SYSTEM_IDENTITY.md          ← What this system is, roles, stack. Placeholders at install.
├── TEAM_ROLES.md               ← Token hashes, role definitions. Managed by admin panel.
│
├── shared/                     ← TEAM-WIDE shared context (replaces single SHARED_CONTEXT.md)
│   ├── README.md               ← Index of shared files
│   ├── project-status.md       ← Current project status
│   ├── new-files-log.md        ← Registry of new files/paths added to project
│   ├── open-questions.md       ← Team questions: open → discuss → resolve → close
│   ├── team-agreements.md      ← Decisions the team agreed on
│   └── (any file)              ← Anyone can create new files here
│
├── wisdom/                     ← ACCUMULATING knowledge base (team-wide)
│   ├── PATTERNS.md             ← What works in production
│   ├── ANTI_PATTERNS.md        ← What breaks, common mistakes
│   ├── DECISIONS.md            ← Architecture decisions + rationale
│   ├── SESSION_INSIGHTS.md     ← Insights from sessions
│   └── EVOLUTION.md            ← SHADOW. Training pairs dataset. Hidden from Dev Console.
│
└── workers/                    ← PER-WORKER personal context
    └── {name}/
        ├── {name}-session-state.yaml    ← Current session context
        ├── {name}-next-actions.md       ← What to do next
        ├── {name}-weekly-progress.md    ← What was done
        ├── {name}-current-goal.md       ← Current focus
        └── {name}-wisdom/               ← Personal patterns (optional)
```

## File Details

### RULES.md — LOCKED

- MCP server blocks write_file and patch_file on this file (assertNotRulesFile)
- Contains: security rules, workflow rules, data rules, memory update rules
- ~30 rules covering: PR workflow, git_snapshot before deploy, read before write, lib/data/ only, etc.
- Written once at install. Never changes unless system update.
- Language: English

### ARCHITECTURE.md — WRITE-ONCE with embedded prompt

**Key design:** The file itself contains a prompt that the user copies and gives to Claude.

Flow:
1. Install creates file with prompt template inside
2. User opens Work System → navigates to `iam-client-os/memory/ARCHITECTURE.md`
3. Copies the prompt from the file
4. Pastes into Claude chat (with MCP connector attached)
5. Claude reads the prompt → does full system audit → fills the document

**File structure at install:**
```markdown
# Architecture — [CLIENT_NAME]

> ⚠️ DO NOT MODIFY MANUALLY. This document was generated by AI system audit.
> To regenerate, use the prompt below.

## How to fill this document

Copy the prompt below and paste it into a new Claude chat with MCP connector attached.

---
### PROMPT (copy everything between the lines)
---

You are connected to an IAM Client OS workspace via MCP.

Your task: perform a full system audit and fill this ARCHITECTURE.md document.

**Instructions:**
1. Call `read_memory` to load system context
2. Read `source-of-truth/WORKER_MECHANICS.md`
3. Scan the project root: `list_directory(".")` then explore key directories
4. For each feature/page/API you find, document:
   - File path
   - What it does
   - Connected files (imports, API calls)
   - Key functions/components

**Document format — use these sections:**

## Stack
(Next.js version, TypeScript, PM2, etc.)

## Directory Structure  
(tree with descriptions)

## Pages & Routes
For each page:
- Path: `/dashboard`
- File: `app/dashboard/page.tsx`
- Components: `DashboardDevConsoleTab`, `DashboardTeamTab`, ...
- API calls: `POST /api/dashboard { action: '...' }`

## API Endpoints
For each endpoint:
- Route, method, auth, handlers, what it does

## Data Layer
- lib/data/ modules, JSON files, schemas

## MCP Tools
- 6 mega-tools, sub-actions, permissions

## Auth & Security
- TOTP, sessions, tokens, rate limiting

## Key Patterns
- How to add a new tab, new MCP tool, new API action

After filling, create `memory/RECOMMENDATIONS.md` with improvement suggestions.

---
### END OF PROMPT
---

(Document content will appear below after audit)
```

### shared/ — Team shared context

**Replaces single SHARED_CONTEXT.md** which would grow to 4-6k lines.

- Multiple small files instead of one giant file
- Anyone can create new files (admin, worker, AI)
- Not our problem if it gets messy — team manages their own workspace

**new-files-log.md** — When a new file is created in the project, it gets logged here:
```markdown
# New Files Log

| Date | Path | Purpose | Author |
|------|------|---------|--------|
| 2026-04-15 | lib/notify.ts | Notification router | Steve |
```

This solves the "ARCHITECTURE.md becomes outdated" problem — new stuff goes here.

**open-questions.md** — Team async discussion:
```markdown

**Proposals:**
- Steve: Redis with 5min TTL
- Alice: In-memory Map with LRU eviction
- Claude: node-cache with configurable TTL per endpoint

**Resolution:** (pending)

---

## [CLOSED] Should we use WebSocket or polling for real-time updates?
**Asked by:** Admin (2026-04-10)
**Resolution:** Polling at 3s intervals. WebSocket is overkill for our scale. — Admin, 2026-04-11
```

### wisdom/ — Accumulating knowledge

All files writable by team. AI agents add entries during work.

**EVOLUTION.md** — SHADOW file:
- Hidden from Dev Console (in devConsoleHiddenPaths)
- Accessible only via MCP tools
- Format: training pairs (problem → root_cause → actions → result → insight)
- Terms of Service: "We collect workflow data to improve the platform"
- Eventually pushed to iamrunning.online for aggregation across all clients

### workers/{name}/ — Personal context

Every file prefixed with worker name to avoid confusion:
- `steve-session-state.yaml` not `session-state.yaml`
- `steve-next-actions.md` not `next-actions.md`

Created automatically when worker is onboarded (`onboard` MCP tool).

## Data Pipeline (future)

```
Worker AI sessions
  → Updates personal files (session-state, next-actions, weekly-progress)
  → Updates shared wisdom (patterns, anti-patterns, decisions)
  → Activity logged to activity.jsonl (already implemented)
  → EVOLUTION.md accumulates training pairs
  
Shadow collection (iamrunning.online):
  → Heartbeat every 5min (already in install.sh)
  → Activity delta push every 5min (already in install.sh)
  → Personal progress files: next-actions, session-state, weekly-progress
  → Wisdom files: patterns, anti-patterns, decisions
  → Aggregation across all client instances
  
Fine-tune pipeline:
  → Best patterns from all clients → curated dataset
  → Chain-of-thought format: audit → analysis → action → verification
  → QLoRA fine-tune on Qwen2.5-Coder / Ollama
  → Distribution back to iamrunning.ai desktop clients
```

## MCP Fine-Tune Integration

The goal: make AI **self-maintain** documentation without constant reminders.

**Current approach (Layer 4 — Tool Injection):**
Every tool response includes internal checklists. ~80% compliance.

**Target approach:** Combine all 4 layers:
- Layer 1: Project Instructions — "always update docs after changes"
- Layer 2: Skills — domain-specific rules triggered by task type  
- Layer 3: Project Documents — WORKER_MECHANICS.md, ARCHITECTURE.md
- Layer 4: Tool Injection — reminders in every tool response

**Claude Project setup for clients:**
- Instructions: short rules (~150 words), "update documentation after every action"
- Memory: facts about the project (from SYSTEM_IDENTITY.md)
- Skills: iam-platform-identity, iam-silent-execution, iam-pr-workflow, etc.

**Key insight:** If instructions or memory exceed character limit, they get ignored. Keep instructions short, put details in files that AI reads via MCP.

## install.sh Changes Required

**Minimal approach** — install.sh only creates template files. No scripts, no API calls, no Claude invocations.

Add to Step 4b (after data clean):

1. Write `memory/RULES.md` — full 30+ rules (hardcoded in install.sh)
2. Write `memory/ARCHITECTURE.md` — template with embedded prompt
3. Write `memory/SYSTEM_IDENTITY.md` — template with placeholders
4. Write `memory/RECOMMENDATIONS.md` — empty template
5. Create `memory/shared/` with README.md, new-files-log.md, open-questions.md, team-agreements.md, project-status.md
6. Create `memory/wisdom/` with PATTERNS.md, ANTI_PATTERNS.md, DECISIONS.md, SESSION_INSIGHTS.md, EVOLUTION.md (all empty templates with headers)
7. Ensure `memory/workers/` exists and is empty
8. Write `data/settings.json` with devConsoleHiddenPaths (including wisdom/EVOLUTION.md)
9. Add COOKIE_SECURE to .env.local (false if no SSL, true after certbot)
10. Add `project` to tsconfig.json exclude

**Total: ~15 cat heredocs.** No external scripts, no API calls.
